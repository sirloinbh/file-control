# file-control

File Control - a personal tool that automates renaming, extracting, moving, and deleting files on my computer

`fctl` is a command-line tool that runs on Node.js (22 or later) alone, with no external packages.
It is named `fctl` so that it does not clash with `fc` (file compare), which Windows ships by default.

## Install

```bash
npm link                     # register the fctl command so it works from any folder
npm unlink -g file-control   # remove the registration
```

You can also run it without installing, with `node bin/fctl.js <command>`.

## Commands

| Command | What it does |
| --- | --- |
| `fctl ls [folder]` | Show the contents of a folder |
| `fctl mkdir <folder>` | Create a folder (including intermediate folders) |
| `fctl write <file> [content]` | Create a file (reads standard input if there is no content) |
| `fctl append <file> [content]` | Append content to the end of a file |
| `fctl cat <file>` | Show the contents of a file |
| `fctl rename <path> <new-name>` | Rename within the same folder |
| `fctl mv <source...> <target>` | Move (into the folder if the target is an existing folder) |
| `fctl cp <source...> <target>` | Copy |
| `fctl rm <path...>` | Send to the Recycle Bin |
| `fctl unzip <archive> [folder]` | Extract (default: a folder named after the archive) |
| `fctl zip <archive> <source...>` | Compress (the extension, such as `.zip` or `.tar.gz`, decides the format) |
| `fctl flatten <target>` | Move the files of subfolders directly under the target and send the empty folders to the Recycle Bin |
| `fctl product-number <target>` | Put the product number in front of video file names |
| `fctl extract-all <target>` | Extract each archive into its own new folder |
| `fctl find-broken <target>` | Find broken files (does not touch any file) |
| `fctl remove-broken <target>` | Show the list of broken files and a confirmation value. With `--yes=<confirmation value>`, it writes a record and sends them to the Recycle Bin |
| `fctl find-duplicates <target>` | Group videos that have the same name or product number, or the same length (does not touch any file) |
| `fctl remove-duplicates <target>` | Show the list of duplicate videos to delete and a confirmation value. With `--yes=<confirmation value>`, it writes a record and sends them to the Recycle Bin |
| `fctl collapse <target>` | Collapse stretches where each folder holds only one folder |
| `fctl normalize <target>` | Put the product number in a file name first, in upper case |
| `fctl find-low-quality <target>` | Find low-quality videos below the resolution or bitrate standard (does not touch any file) |
| `fctl remove-low-quality <target>` | Show the list of low-quality videos to delete and a confirmation value. With `--yes=<confirmation value>`, it writes a record and sends them to the Recycle Bin |
| `fctl ui [--port=<number>] [--no-open]` | Start the local web screen (127.0.0.1, default port 8109). See [Screen](#screen-fctl-ui) below |

Options

- `--force`: Overwrite a file that already exists. Without it, the command stops with an error instead of overwriting.
- `--permanent`: In `rm`, delete permanently without going through the Recycle Bin.
- `--dry-run`: Print only what would change, with `[Preview]` added, and do not touch anything for real.

An unknown option runs nothing and reports an error. Write a name that starts with `-` as `./-name` or after `--` (`fctl rename a.txt -- "-b.txt"`). Every argument after `--` is treated as a name or content, not an option.

PowerShell splits an unquoted dash name such as `-b.txt` into `-b` and `.txt`, so use `./-name` or wrap the name in quotes. When you call a `fctl` registered by `npm link` from PowerShell, the `--` can disappear (checked with a script built like the `npm link` shim), so if you need `--`, run `node bin/fctl.js` directly.

The content of `write` and `append` may start with a single `-`, as in `- item`, but content that starts with `--` and `-h` go after `--` (`fctl write a.txt -- "--- title"`). Be careful: a typo such as `-dry-run` in the content position is used as content.

## Safety measures

- Deletion sends to the Recycle Bin by default, so it can be undone. When the session is not interactive (a service or a scheduled task), permanent deletion is refused.
- **`rm` checks every target before it deletes anything** (#129). If even one target is certain not to be sendable to the Recycle Bin, nothing is deleted and the reason is reported. In `rm a b c`, a and b stay even if only c has a problem. `--dry-run` goes through the same check, so it does not show a target that would really fail as "move to the Recycle Bin".
  - A target whose full path is longer than 259 characters
  - A `\\?\D:\...` prefixed path: moving to the Recycle Bin cannot accept this form. If the same item is still pointed to after removing the prefix, it removes the prefix and sends it. If the path Node normalized differs from the path with the prefix removed (for example when `..` escapes above the drive), it is refused. Other forms such as `\\?\UNC\` and `\\.\` are also refused.
  - A path that contains a name ending in a dot or a space (with or without the prefix): moving to the Recycle Bin (PowerShell 5.1) points to the name with the trailing dot or space removed, so when `dot.` and `dot` exist together it sent `dot` to the Recycle Bin (checked on build 26200). So it is refused. Give `fctl rename` a `\\?\` prefixed path to rename it, then delete it.
  - A target that would be deleted permanently without going through the Recycle Bin (#81). When tested on build 26200, Windows deleted permanently without asking in the following cases and finished as a success, and the old `rm` reported "moved to the Recycle Bin". So it looks at that volume's Recycle Bin settings (the same decision as #100) and refuses. The preview is the same, and on a real delete the Recycle Bin move script checks once more right before deleting.
    - One item is larger than the Recycle Bin maximum size of that volume. For a folder, it uses the total of the files inside (it does not count past links or junctions). On D: (maximum 7164MB), a 7100MB file went to the Recycle Bin, while a 7200MB file, an 8GB file, and an 8GB-total folder (including small files inside) were deleted permanently. If it cannot read the maximum size, it refuses from 1GB.
    - A volume whose Recycle Bin setting is "remove immediately" (`NukeOnDelete`)
    - A drive that is not a fixed disk (removable, network, and so on) or whose type could not be determined. Removable and network drives were not tested. A USB external exFAT disk (E: on this PC) looks like a fixed disk and its Recycle Bin works, so it sends as is.
    - The amount already in the Recycle Bin is not considered. Even when the total exceeded the maximum size, existing items were not emptied and the new item was not deleted permanently.
    - This check adds 0.5 to 1 second per target (the pre-check and the check right before deleting). With many targets, all pre-checks finish before anything is deleted, so there is no output in the meantime. If a target is refused, you can delete it with `rm --permanent`.
    - `extract-all --remove-archives` (the original archive files) and `collapse` (the empty folders it clears), which go through `rm`, also do not delete for the same reason and report a failure. These two commands do not accept `--permanent`, so no hint is added.
  - `--permanent` deletes with Node, so it does not run this check.
  - The inside of a folder is not checked in advance (#190). This avoids reading every item of every large folder. If a folder contains a name ending in a dot or a space (`dot.`, `sp `), moving the whole folder to the Recycle Bin fails with "지정한 파일을 찾을 수 없습니다" (Windows message: "The specified file cannot be found") and nothing is moved (checked on build 26200). On failure, it finds that item inside and reports it, together with a `\\?\` prefixed path you can use to rename it. A path longer than 259 characters inside is not the cause of the failure. A folder containing paths of 274 to 377 characters also went to the Recycle Bin, and the long-path files stayed intact inside the Recycle Bin.
  - If an earlier target contains a later one (`rm a a/b`), a real run deletes a and then stops with "Path does not exist", and `--dry-run` reports "Overlaps an earlier item".
- **Files in use** (#97): sending a file that another program has open, or a folder that contains such a file, to the Recycle Bin fails without an error dialog (build 26200, checked in an interactive session; the other files in the folder were not moved either). It reports that reason in Windows' own wording, and if it finds a file that another program opened while blocking writes, it reports that name too. There is no time limit on the Recycle Bin move. The move takes time in proportion to the number of files (15 to 25 seconds for a 50,000-file folder), and interrupting it midway left some files in the folder in neither the original place nor the Recycle Bin.
- Writing, renaming, moving, copying, and compressing do not overwrite an existing target without `--force`.
- When moving to another drive, the source is deleted after the copy finishes.
- `mv` checks everything first, and if a source and a target overlap, several sources gather into the same target, or it tries to move the current folder, it moves nothing and reports an error.
- `mv --force` does not delete the existing target; it sets it aside for a moment and deletes it after the move finishes. If the move fails, it restores it.
- When `cp --force` merges folders (#140), in the following cases it checks all sources first and, without copying anything, reports an error. In the past, Node finished without an error, copied only part, or wrote past a link.
  - A file and a folder mismatch inside (the source is a folder but the target is a file, or the reverse)
  - A link or junction exists at the same position in the target (including the top)
  - A link or junction of the source lands where an item already exists in the target
  - The kind of the top-level target differs
  - Several sources that gather under the same name (`cp a/x b/x target`) fall into the cases above against each other
- Copying links and junctions inside a source folder (#142): on Windows, `cp` follows a junction and **copies the contents of what it points to**. A folder symbolic link is copied as a link (checked on build 26200, Node 24.21). So if any of the following links exists anywhere in the sources, it checks all sources first, and even in the preview it copies nothing and reports an error. In the past, it copied endlessly until Node finished without an error.
  - A link that points to the source itself or a folder above it (`src/loop` → `src`), or a link inside the source that points to a folder above itself (`src/a/b/up` → `src/a`)
  - A link that points to the target, a folder above it, or something inside it
  - A loop beyond a junction. Like `cp`, it follows links and looks for a link that points to a folder it already passed (`src/out` → `X` and `X/self` → `X`, or `X/back` → `src`). It compares by the file ID of the folder instead of the path text.
  - If it cannot read a folder inside the source, it cannot check, so it does not copy.
  - Node cannot tell a junction from a folder symbolic link, so it follows symbolic links like junctions too. So even a symbolic link that would be copied only as a link is refused if there is a loop above or an unreadable folder beyond it. A junction that points to somewhere else inside the source or to an unrelated folder has its contents copied. A broken link is not examined.
  - `mv` to another drive also moves by copying, so it is refused the same way and the source is left as it was. However, whether it is the same drive can only be known by actually moving, so the preview does not report it.
- `zip` reports an error before deleting anything if it is asked to bundle the archive file itself.
- `zip` does not bundle together sources whose top-level names are the same (`p/f.txt` and `q/f.txt`; on Windows this includes names that differ only in case), because only one would remain when extracted over each other from the archive. The preview is the same. Also, on Windows, it does not bundle when the same folder in the archive (including the top) holds both a name that looks like an 8.3 short name (`LONGER~1.TXT`) and a long name that could receive that short name (`longername.txt`) (#159). This is because when extracted onto a volume that makes short names, one overwrites the other depending on the extraction order. If you give a source as a short name, `tar.exe` writes that short name as is as the entry name. Whether they can overlap is estimated generously from the part before the extension and the first letter of the name (Windows cuts by OEM code page bytes and adds a hash or drops letters, so it assumes they can overlap when a non-ASCII letter is involved), so it can also refuse names that do not really overlap. However, an ASCII name that is originally in 8.3 form (`photo.jpg`, `Photo.Jpg`, `noext`: a name of 1 to 8 characters, an extension of 0 to 3 characters, at most one dot, and none of the space and `+,;=[]` characters) is not made a short name by Windows regardless of case, so it is not considered to overlap even when it sits with `photo~1.jpg` (#205; `unzip` and `extract-all` are the same).
- The format of `zip` is decided by the extension and is case-insensitive (`X.ZIP` is also zip, `x.TAR.GZ` is also gzip). The only exceptions are the compress extensions `.Z`, `.taZ`, and `.tZ`, which `tar.exe` distinguishes by case: written this way it is compress, `x.tar.z` and `x.tz` are an uncompressed tar, and `x.taz` is gzip. When a compression extension (`.gz`, `.bz2`, `.xz`, `.zst`, `.lzma`, `.lz`, `.lz4`, `.lzo`, `.lrz`, `.grz`, `.uu`, `.Z`) follows an extension that `tar.exe` reads as a format (`.cpio`, `.iso`, `.ar`, `.shar`, `.xar`, `.warc`, `.mtree`, `.zip`), it wraps that format in that compression (`x.cpio.gz` is a cpio inside gzip, #164). An extension that is not read as a format, such as `.jar.gz`, is a tar inside gzip, the same as just adding `.gz`. A name that compresses 7z again, such as `.7z.gz`, is refused because `tar.exe` cannot extract it. If there are several layers of compression extensions (including tar+compression extensions such as `.tgz` and `.txz`), it wraps them the way `tar.exe` peels them layer by layer from the end (#193). `x.tar.gz.gz` is a tar inside two layers of gzip, and `x.cpio.gz.xz` is a cpio inside gzip inside xz. `x.cpio.Z.gz` is a cpio inside compress inside gzip, and aliases such as `.tz2` (`.tar.bz2`) and `.tzo` (`.tar.lzo`) also count as layers. A name that wraps 7z in several layers, such as `.7z.gz.xz`, is also refused. The entry names of a multi-layer name are judged by the innermost format (#212). Outer compression layers do not change the encoding of entry names, so `x.tar.gz.gz`, `x.gz.xz`, and `x.tgz.gz` skip the OEM check like `.tar.gz`, `.gz`, and `.tgz` (checked on the English Windows in CI), while a name whose inside is zip or cpio or a format that was not checked, such as `x.cpio.gz.xz` and `x.zip.gz.gz`, refuses names that are not in the OEM code page. A name with 25 or more compression layers (such as `x.gz` repeated 25 times) is refused because `tar.exe` can bundle it but cannot extract it again ("too many filters"), and a name for which the temporary file name used while bundling (`.fctl-new-...` plus the extension layers) could reach the 255-character limit while leaving 4 characters for the number (a name that is very long, with the last extension more than about 220 characters) is also refused in advance (#213). The `.lz4`, `.lzo` (including `.tzo`), `.lrz`, and `.grz` compressions are not built into `tar.exe`, so it runs an external program (`lz4`, `lzop`, `lrzip`, `grzip`); if that program's `.exe` is not on the PATH (`tar.exe` does not run `.cmd` or `.bat`), `zip` refuses and states the reason, including in the preview (#230). If it exists, it leaves the work to `tar.exe`. `.lz`, `.lzma`, `.zst`, and `.uu` are built in, so they do not matter. `tar.exe` looks for such external programs in the current folder before the PATH, so fctl always runs `tar.exe` from the folder where `tar.exe` lives (System32), so a program planted in the current folder, such as `lz4.exe`, does not run (#242). When extracting, it identifies the compression by content, not by name, so if you `unzip` or `extract-all` (including the preview) a file compressed with lz4, lzop, or similar and that program is missing, it reports a reason that names the program (#241). `zip` and `unzip`, including the preview, refuse the following two cases first (#228). A name segment longer than 255 characters in the archive path or the extraction folder path cannot be created, so it is refused. Also, if the folder `tar.exe` moves into (the extraction folder of `unzip`, the parent folder of the `zip` source) is longer than 258 characters, `tar.exe` fails with "could not chdir", so it is refused. This does not depend on the long-path setting (measured both on this PC with LongPathsEnabled=0 and on CI with long paths turned on). `extract-all` extracts into a temporary folder next to the archive (`.fctl-new-...`, a path about 30 characters longer than the archive's folder), so for an archive where that temporary folder would reach this limit while leaving 4 characters for the number, it reports a failure, including in the preview (#238). It applies when the archive's folder is longer than roughly 220 characters, and the reason states the length of the archive's folder and how much it must be shortened. Even when the final extraction folder is within the limit, it cannot extract in this case. The archive path itself and the paths of extracted items may be longer than 260 characters.
- `zip` bundles under a temporary name and then replaces the existing archive. While bundling, the existing archive stays under its original name, and if it fails it is left as it was. If the archive is inside the folder to bundle or the folder to bundle has a link, it sets it aside as `.fctl-old-*` before bundling so it is not bundled along, and restores it on failure.
- On Windows, `unzip` (including `extract-all`) does not extract when the same folder in the archive holds both an item that looks like an 8.3 short name (`LONGER~1.TXT`) and an item that could receive that short name (`longername.txt`) (#188). Whether they can overlap is estimated the same way as `zip` (folders that differ only in case count as the same folder), and because the list comes out in the code page, a non-ASCII letter and `?` count as a letter that can be anything. Also, when extracting into an existing folder, if a `~N` entry would point, as a short name, to a file or folder with a different name that already exists in that folder (extracting `LONGER~1.TXT` into a folder that has `longername.txt`), it would overwrite that file or mix into that folder, so it does not extract. ASCII names are judged by the short names that actually exist on the volume, so an existing file with exactly the same name is overwritten as before, and it does not trigger on a volume that does not make short names. A `~N` entry that contains non-ASCII letters (`한글긴~1.TXT`, an example Korean name) cannot be checked by path, so it is compared with the existing names by the same estimate, and it can be refused even on a volume that does not make short names or for an existing file with exactly the same name. A folder name that contains such letters counts as every existing non-ASCII folder at that position. The preview is the same.
- `unzip` does not ask for a password. An archive with a password fails.
- Before extracting, `unzip` and `extract-all` add up the sizes in the archive's list (each file rounded up to the volume's cluster size (at least 4KB), plus 1KB per entry) and compare it with the free disk space at the destination. If less than 1GB would be left after extracting, that archive is not extracted. It also does not extract if it cannot confirm the free space or cannot read a size from the list. The size in the list is a value the archive wrote down, so it can differ from the real one (a value that makes a large empty file without content, such as `size=` in mtree text, is counted as is). When extracting into an existing folder, the size reduced by overwriting is not subtracted. The preview shows the extracted size together. The `extract-all` preview compares each archive separately, so if several together run out of space, a later archive can be refused in the real run (`--remove-archives` sends to the Recycle Bin, so it does not free space).
- Commands that use `tar.exe` (`zip`, `unzip`, `extract-all`, and the archive check of `find-broken` and `remove-broken`) do not pass on the `TAR_READER_OPTIONS` and `TAR_WRITER_OPTIONS` environment variables. This is because if an option such as `mtree:checkfs` is turned on, a local file that text in an archive points to could be copied into the extraction folder.
- **Device names** (#53, #135): the cleanup commands (the commands that go through `grant`) do not handle names that PowerShell treats as a device rather than a file, and skip them with a reason. Which names are devices follows the rules below.
  - The basic commands (`write`, `mkdir`, `rename`, `mv`, `cp`, `zip`, `unzip`) **do not newly create** such names. Node creates them literally, but PowerShell and Explorer cannot open or delete them. Windows removes a trailing dot or space, so `com1 ` and `Nul.mp4.` are also treated as the same device names. An existing file can be read and overwritten, and you can bring it out by renaming it to an ordinary name with `rename` or `mv`. Creating an ordinary name inside an already existing folder of the above kind (such as `Con.Air`) is not blocked.
  - A path that contains a name that is exactly a device name (`nul`, `CON`, `Com1`, `lpt¹`, `CONIN$`, including `nul.` with a trailing dot or space, excluding `COM0` and `LPT0`; this also includes `CONa.txt` inside such a folder) is not accepted as an argument of `zip` and `unzip` or as a target of `rm` (Recycle Bin). On build 26200, `tar.exe` failed by opening the device, and the move to the Recycle Bin also failed. Rename it and run again. `rm --permanent` deletes with Node, so it is accepted.
  - A file with a device name inside a folder to bundle is bundled and extracted by `tar.exe` with the same content, and handled as is. If a move to the Recycle Bin fails because an item that is exactly a device name is inside a folder, it reports that item. The names inside a folder that `cp` and `mv` move, and the entry names inside an archive that `unzip` extracts, are not checked either, so extracting an archive made on another OS can create a file such as `Nul.mp4`. `extract-all` does not extract an archive that contains such an entry and reports a failure.
  - Windows 11 24H2 or later (build 26100 or later, including Windows Server 2025): it refuses only a name that is exactly a device name (`CON`, `PRN`, `AUX`, `NUL`, `COM1` to `COM9`, `LPT1` to `LPT9`, `COM¹`, and so on) or has just one extension attached (`Nul.mp4`, `con.txt`, `Con.Air`), and `CONIN$` and `CONOUT$`. `Con.Air.1997.mkv` and `nul.tar.gz` with two or more dots, `Nul .mp4` with a space before the dot, and `COM0` and `LPT0` are handled, because on build 26200 PowerShell, `tar.exe`, and the Recycle Bin move were confirmed to treat them as the same file.
  - Earlier versions (Windows 10, Windows 11 23H2 or earlier, Windows Server 2022): it could not check, so it refuses every name that starts with a device name (including `Con.Air.1997.mkv`).
- **Hard links** (#48): for a file with a link count of 2 or more, you cannot tell from the path alone whether it is the same file as one outside the target. Changing the content also changes the content under the other name, so only writing content is refused.
  - Refused: `write` (overwriting, `--append`), `cp --force` that overwrites a hard link (including a file in the folder being merged), and the write permission of `grant`
  - Allowed: reading, `rename`, the replacement by `mv --force`, `rm`, and `unzip` replacing an existing file. On build 26200, these operations were confirmed to only rename or delete, leaving the content under the other name as it was.
- `zip` and `unzip` do not run and report an error if the path or the name to bundle has a character that is not in the system ANSI code page (an emoji, `é` on Korean Windows, Hangul jamo that came from macOS, and so on) or if a name ends in a dot or a space. This is because `tar.exe` takes arguments in ANSI and may change such a character into another letter and handle a different file. Also, when bundling into zip or cpio (including `.tar.zip` and `.tar.cpio`) or into a format that has not been confirmed not to go through OEM, the entry names (the source names and the names inside the folder to bundle) are written in the OEM code page, so it also refuses a character that is not in OEM (`¹` and `€` on English Windows (ANSI 1252, OEM 437)) (`COM¹` -> `COM1`). The archive path, the parent folder of a source, the extraction folder, and the entry names of the confirmed formats (`.tar`, `.tgz`, `.tar.gz`, `.tar.bz2`, `.tar.xz`, `.tar.zst`, `.gz`, `.taZ`, `.7z`, `.jar`, `.iso`, `.xar`, `.mtree`, `.warc`) do not go through OEM, so they are not refused. On Korean Windows, ANSI and OEM are both 949.
- While the cleanup commands walk under the target, if a subfolder is replaced by a link or junction (whether outside the target or another folder inside it), they notice it by checking the real path after reading the folder, and report an error instead of continuing with a partial list (#46).
- `--dry-run` tells you in advance about operations that would fail, such as a path that does not exist, an overwrite conflict, and moving into itself. However, permissions, disk space, file locks, names that cannot be used on Windows, paths that go through links or junctions, conflicts inside a folder being copied, renaming the current folder or one above it, and damage or conflicts in archive content can be known only by really running.

## Flatten

`fctl flatten <target>` moves the files of subfolders directly under the target. You can check first with `--dry-run`.

- **It does not overwrite.** If names collide, it adds a number such as `a (2).mkv`. It does not use `--force`.
  - A file that keeps its original name receives the name first (#63). If `ABC-123 Title/x.mp4` and `z/ABC-123 Title.mp4` both exist, the one with the original name becomes `ABC-123 Title.mp4` and the one that takes the folder name gets the number. However, a pair that receives the same prefix (`ABC-123/video.mp4`, `ABC-123/Subs/video.en.srt` → `ABC-123 video.*`) receives names even before that, so the pair is not broken.
  - If a file receives the same name as its own outer folder (`ABC-123 Title.mp4/x.mp4`), the folder still exists at the time of moving, so it becomes `ABC-123 Title (2).mp4`. If it renamed the folder to a temporary name and was interrupted midway, the file would stay in a leftover folder that the next run does not move, so it does not clear it. Remove the number with `rename`.
- **Name**: if the file is the only file in that folder and the folder name is more detailed, it uses the folder name. `ABC-123 Title/abc_123.mp4` becomes `ABC-123 Title.mp4`. If it cannot decide, it keeps the file name, and it does not change the extension.
  - **File names without information** (`video`, `movie`, `sample`, `영상` (video), `파일` (file), and so on, #71): it makes sure the information in the folder name is not lost when the folder is removed. If it is the only file in that folder, it also uses a folder name that is not a product number (`PART-01/video.mp4` → `PART-01.mp4`, `BD-123`, `Summer video collection`). If the outer folder has a product number, it uses that first. If there are several files, it prepends the nearest folder name (`ABC-123/video.mp4`, `ABC-123/sample.mp4` → `ABC-123 video.mp4`, `ABC-123 sample.mp4`). If the nearest folder has no information, such as `1080p/`, it goes up to the folder above to find one. If the part before the first dot has no information, as in `video.en.srt`, it receives the same prefix, so the subtitle pair is kept. If the attached name exceeds 255 characters, it moves with the original name. In the report, both appear as "folder name used".
  - **It keeps both the outer folder and the nearest folder name** (#150). When the only file receives the nearest folder name, it prepends the product number of a folder outside that folder (or a usable title if there is none): `ABC-123/CD1/video.mp4`, `ABC-123/CD2/video.mp4` → `ABC-123 CD1.mp4`, `ABC-123 CD2.mp4`. It prepends it even when the outer folder holds only one file (#168; even a single `Show/CD1/video.mp4` becomes `Show CD1.mp4`). However, if there is only one file inside the product-number folder, it picks the product-number folder name first, so it uses only that name as before (a single `ABC-123/CD1/video.mp4` → `ABC-123.mp4`). The folders in between are also attached by the rule below (`Show/1080p/CD1/video.mp4` → `Show 1080p CD1.mp4`). When it prepends the folder name above as a prefix, it attaches, from the outside, any usable name among the folders in between or a quality or codec name: `Show/1080p/video.mp4`, `Show/720p/video.mp4` → `Show 1080p video.mp4`, `Show 720p video.mp4`. It does not attach container folder names such as `Subs`, `자막` (subtitles), `Videos`, and `새 폴더` (new folder), a folder with a subtitle word in it (`English Subs`), a language folder that holds only subtitles without video (`English`, `한국어` (Korean)), or a folder under a subtitle folder (`Subs/English`), so even `Show/1080p/Subs/video.en.srt` keeps its pair as `Show 1080p video.en.srt`. A name that is already included is not attached again, and if the combined name exceeds 255 characters, it uses the name from before combining.
  - It is the same when a prefix is attached because there are several files (#178). If the chosen folder is not a product-number folder, it prepends the outer title folder, so `Show/CD1/video.mp4`, `Show/CD1/video.en.srt` → `Show CD1 video.mp4`, `Show CD1 video.en.srt`. With or without subtitles, `Show` and `CD1` stay together. It is the same even when the chosen folder is the folder right above, so `Collection/Show/video.mp4`, `Collection/Show/sample.mp4` become `Collection Show video.mp4`, `Collection Show sample.mp4`. If the outer name already contains the chosen name (`Show CD1/CD1/`), it is not attached again. The 255-character limit is judged by the prefix and the part before the first dot (leaving 30 characters for the extension and the language mark), so even near the limit `video.mp4` and `video.en.srt` receive the same prefix.
  - A one-letter name such as `a.mp4` may be an abbreviation, so it is changed only when the folder is a product-number folder. Common folder names such as `새 폴더 (2)` ("New folder (2)"), `Videos`, and `Downloads`, and folder names that hold only quality or codec such as `H264`, `1080p`, and `WEB-DL`, are treated as having no information and are not used.
  - For the prefix too, it uses a product-number folder among the folders above first and attaches the in-between folder names after it (`ABC-123/Extras/video.mp4` → `ABC-123 Extras video.mp4`). It does not use subtitle folder names such as `Subs` and `자막` (subtitles). For subtitle files (`.srt`, `.ass`, `.vtt`, `.sub`, and so on), it leaves out the outermost subtitle folder (`Subs`, `English Subs`, or a language folder that holds only subtitles without video, such as `English` and `한국어` (Korean)) and chooses the name to match the video-side folder (#211, #233): `Show/CD1/video.mp4`, `Show/CD1/English/video.en.srt` → `Show CD1 video.mp4`, `Show CD1 video.en.srt`. If the subtitle folder is split with the same structure as the video (if the video side has a folder of the same path that holds video), it uses the video-side folder name (including its spelling) and counts the file as a file in the same folder as the video: `Show/Season 1/video.mp4`, `Show/Subtitles/Season 1/video.srt` → `Show Season 1 video.mp4`, `Show Season 1 video.srt` (`Subs/Show/CD1/` is the same). Among the folders deeper than that, a usable name (`Forced`, `Full`) is attached with a dot after the part before the first dot, to tell them apart while keeping the pair with the video (it is not attached if attaching would exceed 255 characters): `Show/video.mp4`, `Show/Subs/Forced/video.srt`, `Show/Subs/Full/video.srt` → `Show video.mp4`, `Show video.Forced.srt`, `Show video.Full.srt`. An inner folder made only of subtitle or language words (`Subs/English`) is not attached. A language folder that holds video (a dubbed version, a lecture) is used as a name like any other folder: `Show/English/video.mp4`, `Show/Korean/video.mp4` → `Show English.mp4`, `Show Korean.mp4`, and several files in `Show/English/CD1/` → `Show English CD1 video.mp4`. For the outer title, it picks a folder that is not a language folder first and uses a language folder only when there is none (`Korean/Lesson 1/video.mp4` → `Korean Lesson 1.mp4`). A file that is not a subtitle (`Subs/Fonts/font.ttf`) does not pick a folder inside the subtitle folder. A folder that holds a title together (`Movie [Eng Sub]`) is not treated as a subtitle folder and is used as before. A product-number folder is not attached even inside a subtitle folder and is picked first (`Subs/ABC-123/video.srt` → `ABC-123.srt`). Limitation: if a subtitle is in a subfolder whose name is not a subtitle or language folder (`ABC-123/Extras/video.en.srt`), its prefix differs from the video (`ABC-123 video.mp4`) (`ABC-123 Extras video.en.srt`).
  - The folder's product number usually remains in the file name, so `product-number` may run before or after `flatten`.
- **It refuses repositories.** If there is a `.git`, `.hg`, `.svn`, `.jj`, or a bare repository under the target, or the target is inside one, it moves nothing and reports an error. If the target is an ordinary subfolder of a repository (`r/src`), it does not refuse. The repository is not broken and tracked files can be restored with git, but untracked files cannot be restored.
- **Items it does not move**: links, names that Windows interprets in different ways (a trailing dot or space, and device names such as `Nul.mp4` and `con.txt`), leftovers named `.fctl-old-*` and `.fctl-new-*`, and files inside `$RECYCLE.BIN` and `System Volume Information`. It reports them with the reason.
- **Program folders are left whole** (#65). It moves none of the files inside and reports "Skipped" once for the folder, not for each file. That folder and the folders above it are not empty, so they are not deleted.
  - A folder named `node_modules`, `bower_components`, `__pycache__`, or `site-packages`
  - A folder that has a project marker file directly inside: `package.json`, `pyvenv.cfg` (a Python virtual environment), `pyproject.toml`, `setup.py`, `Cargo.toml`, `go.mod`, `pom.xml`, `build.gradle`, `CMakeLists.txt`, `composer.json`, `Gemfile`, `*.sln`, `*.csproj`, and so on
  - A folder that has an executable (`.exe`) and a DLL together directly inside. If there is only an executable or only a DLL, it moves them as ordinary files.
  - A folder with the hidden attribute (it is not deleted even when empty). A folder with only the system attribute is treated as an ordinary folder, because that attribute is often added when decorating a folder icon.
  - If the target itself has the marker files above or an executable and a DLL together, or the target is inside a folder such as `node_modules`, it moves nothing and reports an error. Choose a folder below it as the target.
  - **A folder above the target** (#148): even if a folder above the target has a marker file directly inside or has an executable and a DLL together, it moves nothing and reports an error. If `myproj/package.json` exists, it does not handle `myproj/src` and `myproj/src/lib`. It looks at any number of levels up. However, it does not look at places where downloaded files easily land by accident: a drive root, the user folder and above, the default folders directly under the user folder (`Downloads`, `Desktop`, `Documents`, `Pictures`, `Videos`, `Music`, `OneDrive`, and so on), and the default folders directly under the OneDrive folder (`OneDrive\Desktop`, `OneDrive - Company\Documents`, and so on). A `user-folder\myproj` or `OneDrive\app` that the user created is examined. So even if `Downloads\package.json` exists, it can handle `Downloads\videos`, and if `Downloads\proj\package.json` exists, it blocks `Downloads\proj\src`. For a marker file that landed by accident anywhere else (`D:\data\package.json`), move the file named in the error and run again.
- **Files with the hidden or system attribute** are not moved and are skipped with a reason. The attributes are read with PowerShell in one go (including the OneDrive folder; it passes along the folders `walk` saw as they are), and if it cannot read them it moves nothing and reports an error. Each run takes about 0.5 second more. On other operating systems it does not look at attributes.
- **Folder settings and preview files** (`desktop.ini`, `Thumbs.db`, `ehthumbs.db`, `.DS_Store`) are not moved and are not counted in the folder's file count. So the folder name can be used even if `desktop.ini` is there. If only such files are left in the folder that held a moved file, it is seen as an empty folder and sent to the Recycle Bin together.
- The judgments above look only at names and attributes. It cannot recognize a program folder that has no marker file (an executable and a data folder, for example). **There is no undo**, so check with `--dry-run` first.
- The names in `--dry-run` can change at run time. If another program creates the same name in the meantime, a number is added.
- **How it moves** (#73, shared by `flatten`, `product-number`, and `normalize`)
  - For a file, it creates a hard link under the new name and then deletes the original name. A hard link fails if the same name already exists, so it does not overwrite a file another program created in the meantime.
  - If the source is locked and it cannot delete the original name, it deletes the new name it created and rolls back. If a run is interrupted midway, two names with the same content can remain. When you run again, all three commands skip that file and report it as "another name of the same file", so you can delete one side. `flatten` also recognizes the case where the leftover is under a numbered name (`x (2).txt`).
  - On a drive that cannot use hard links (FAT32, exFAT, and so on) and for folders, it first creates an empty placeholder file and then moves over it, as before. In this case, an empty file can remain if it is interrupted midway. When you run again, `product-number` and `normalize` report it separately as an "empty file" (the message says the name is an empty file). `flatten` avoids it by adding a number as usual, because an empty file can also be a normal file.
  - A name created with a hard link does not get an 8.3 short name.
  - **Files moved by hard link in the OneDrive folder too** (#145). This is a measurement taken in a test folder inside the OneDrive folder on this PC (Windows 11 build 26200, personal OneDrive 26.195). It was not checked with a company account or other versions.
    - Hard links were created for both downloaded files and cloud-only files (files turned into free space). So it does not fall back to the placeholder method. Cloud-only files were not downloaded when a hard link was created or moved.
    - A cloud-only file moved with `flatten` and `normalize` downloaded its original content as is when opened after the sync finished. `product-number` was not tested but uses the same move function.
    - Whether the sync recognizes this move as a rename (the web version history, whether shared links continue) has to be checked on the OneDrive web, so it is not known yet (#145).
- **Failure**: even if one file fails, for example a locked file, it keeps moving the rest, shows the list of failures, and ends with exit code 1.
- **Unreadable folders** (#74): if even one subfolder cannot be read, it moves nothing and ends with an error. This is because the empty-folder cleanup decides after seeing everything inside the folders.
- **Empty folders**: if the folder that held a file moved this time becomes empty, it is sent to the Recycle Bin. The empty folders inside it go along. Other folders that were empty originally (`Inbox/`) are not touched. Folders that still hold a skipped or failed file, leftover or system folders, and the current folder and the ones above it are kept. If some folder could not be deleted, it ends with exit code 1.
  - **It sends them in batches** (#67): it sends 100 folders at a time to the Recycle Bin with one PowerShell run. Node checks again for each batch, and PowerShell also checks again, right before deleting each folder, the real path (that it was not replaced by a junction), that it is a folder, and that no file or link has appeared inside. On this PC, a full run for 100 folders (one file each) took 5 seconds. The old method took 13 seconds for 20.
  - **Time limit**: if a batch exceeds 30 seconds plus 1 second per folder (for example when it stalls at an error dialog), it ends PowerShell and treats only the folders reported as processed as deleted. The one folder that was being processed is left with "Not processed because the time limit was hit (an error dialog may have appeared)...", and the folders after it are sent again as a new batch. If it hits the limit right at the first folder of a batch 2 times in a row, it leaves the remaining empty folders undeleted. For the remaining folders, try deleting them in Explorer to find the cause. In a locked-down environment (Constrained Language Mode and the like), if PowerShell cannot create the type used for path checking, it does not delete the empty folders and reports that reason.
  - **Drives that may have no Recycle Bin**: for a drive that is not a fixed disk (USB, network, and so on) or whose type is unknown, it may be deleted permanently, so it leaves the empty folders undeleted. The same applies to a non-interactive session and a volume whose Recycle Bin setting is "remove immediately" (#81; empty folders were also deleted permanently). Moving files is done as usual. `--dry-run` also shows that it will leave them, for the same reason.
- **Progress display** (#67): in a real run, each time a file or a folder is done, it prints one line to standard error, such as `Move: a\x.txt -> x.txt`. Even if it is interrupted midway, what was already done stays on the screen. The final report is still printed once more to standard output as now. `--dry-run` prints no progress lines.
- A protected path, what is inside it, and a folder that contains a protected path cannot be used as a target.
  - System folders: `C:\Windows`, `Program Files` (including the 64-bit folder even in 32-bit Node), `Program Files (x86)`, `ProgramData` (`C:\Users\All Users`), `C:\Recovery`
  - The `$Recycle.Bin` and `System Volume Information` that exist on each drive, and every drive root (`D:\` and so on). The Recycle Bin is created on the first `rm`, so a root is blocked regardless of whether it exists now. It does not recognize the root of a volume mounted on a folder.
  - The user folder itself and the hidden settings folders directly under it (`AppData`, `.ssh`, and so on)
  - Another user's profile itself (under `C:\Users`) and its hidden settings folders. It finds the profile folder as the parent of `%PUBLIC%`, and applies this rule only when my user folder is directly under it.
  - The default profile `C:\Users\Default` is blocked as a whole. `C:\Users\Public` can be used.
  - A folder whose real path you have no permission to see also cannot be checked, so it is not accepted.

## Screen (fctl ui)

You use fctl from a browser screen instead of terminal commands (#250). The screens are being added in turn. For now there is only the common frame and the first screen (#251), and the command category menu shows "Coming soon" until its screen exists.

```bash
fctl ui                  # start http://127.0.0.1:8109/ and open it in the default browser
fctl ui --no-open        # do not open the browser; print only the address
fctl ui --port=8200      # start on another port (0 means a free port)
```

- It can be reached only from inside this PC (`127.0.0.1`). To stop it, press Ctrl+C in the window that started it.
- The default port is 8109 (slot 09 of the project-standards port assignment). If another program already uses the port, it does not move to another port and fails right away. Check what uses it with `netstat -ano | findstr :8109`, or pick another port with `--port`.
- Without external packages and client JS, the server builds the HTML with Node's built-in module (`node:http`) and sends it. It supports both a light and a dark screen, and in a narrow window it wraps long paths so no horizontal scroll appears. Every path and name shown on the screen goes through HTML escaping.
- It blocks requests that another website makes the browser send (CSRF) and DNS rebinding (#252). A request whose `Host` is not `127.0.0.1:<port>` or `localhost:<port>` is rejected. A request that changes files is accepted only from a button on the screen (POST), the `Origin`, if present, must be the same address, and the form must contain the random token made when the server started. When you restart the server the token changes, so open the screen anew. The body is accepted up to 64KiB. Every response carries a `Content-Security-Policy` that blocks scripts (inline styles only), `X-Frame-Options: DENY`, and `Referrer-Policy: no-referrer`.
- Folder picking (`/pick`, #254): pressing "Choose folder" next to the path input shows the frequently used places (Downloads, Desktop, Documents; the OneDrive ones if they moved there) and the list of drives. You click a folder to enter it and go up with "Up"; subfolders are shown in name order, and each folder's file count and size are shown as a summary. Pressing "Choose this folder" returns to the original screen with the path filled in. `C:\Windows`, `C:\Program Files`, the user folder itself, and the hidden settings folders of the user folder (`AppData`, `.ssh`, and so on) can be looked into but cannot be picked, and the reason is shown. Short names (`C:\PROGRA~1`), case, and junctions are resolved to the real path for the decision, and the picked value is also the real path. It does not open network and device paths (`\\server\share`, `\\?\`, `\\.\`), and it does not open folders from an address opened from another site. For the frequently used places, it uses the locations registered in Windows (User Shell Folders) first. It shows up to 1000 subfolders. A folder that has locked system files (such as `C:\DumpStack.log.tmp`) also opens (`fctl ls` is the same).
- The screen code is in `src/ui/`.

## Add product numbers

`fctl product-number <target>` puts the product number in front of the names of the video files under the target. `ABC-123 Title/video.mp4` becomes `ABC-123 Title/ABC-123 video.mp4`. It does not move files. You can check first with `--dry-run`.

- **Format**: like `ABC-123`, 2 to 6 English letters, a hyphen, and 2 to 5 digits. The detailed rules are in `src/product.js`.
- **Targets**: it changes only files with a video extension. `.ts` and `.mts` count as video only when the content is a transport stream, so that it does not change TypeScript sources.
- **Where it looks**: the file name, the metadata title, the folder names (under the target, starting from the nearest folder), and the comment, in that order. It reads metadata only for the MP4 family (`.mp4`, `.m4v`, `.mov`, `.3gp`), `.mkv`, and `.webm`.
- **If a number already exists**, it skips the file regardless of position. If it equals the number to be added, it counts as present even when the case differs or letters are attached (`ABC-123-01`, `abc-123`).
- **Lowercase words in a file name** (`trip-2023`, `intro-01`) are not certain to be a number. If the title, folder, or comment has a different number, it does not pick one and reports a conflict.
- **A number with letters attached** (`ABC-123-01`, `ABC-123A`, `1ABC-123`) in the file name that differs from the found number is reported as a conflict, and no further number is added in front. If it is the same number, or the same number written without a hyphen (`ABC123`, `ABC_123`, `ABC 123`), it is treated as already present. A date form with year-month-day all written (`ZZZ-2024-05-01`) is not seen as a number. A year-month (`MEET-2024-05`) or a date written together (`TRIP-2024-0501`) is seen as a number with letters attached and becomes a conflict.
- **If it finds none**, it does not touch the file and reports it in a list. If the numbers of the title and the folder conflict, it does not pick one and reports it. It does not change links and reports them.
- **If it cannot read the metadata** (damaged, a different format, read limit exceeded), it reports that reason too. It also writes it when it renames by the folder number or reports a conflict. You cannot tell whether the title had a different number, so check.
- **It does not overwrite.** If the same name exists, it skips and reports.
- **An unreadable subfolder** (#74) is reported as "Skipped" and the other files are still changed. Files are changed one by one, so a folder it could not see does not affect other files. If it cannot read the target itself, it changes nothing and ends with an error.
- **There is no undo.** For OneDrive online-only files, reading the metadata can trigger a download. `.ts` and `.mts` read the beginning regardless of name, so this can happen even for a source file without a number.

## Normalize file names

`fctl normalize <target>` moves the product number in the file names under the target to the front, in upper case. `Video ABC-123.mp4` becomes `ABC-123 Video.mp4`. It does not move files. You can check first with `--dry-run`.

- **It does not change words that are not the number, or the extension.** It only tidies the separator characters and empty brackets where the number was removed. It does not cut off tails such as `.en.srt` and `.7z.001`.
- **It does not change lowercase words by default.** Names such as `trip-2023.mp4` and `node-22.1.0.msi` may not be numbers, so it only reports how they would change. With `--include-lowercase`, it changes them.
- **It does not overwrite.** If a result collides with an existing item or with the result of another file, it changes neither and reports it.
- **A name that changes only in case** is changed through a temporary name.
- **Left as they are**: a name with several numbers, hidden files, temporary files that start with `~` (`~$document.docx`, `~abc-123.mp4`), a name ending in a dot or a space, links, leftovers, and files inside system folders. Of these, hidden files, temporary files, and names ending in a dot or a space are not reported.
- **If a repository is inside, it refuses everything.** A bare repository is the same. Changing ref and object names would break the repository. It also refuses when the target is inside `.git` or a bare repository folder. An ordinary subfolder of a working tree such as `work/src` can be restored with git, so it changes it.
- **It does not change files being downloaded and reports them.** These are files with a download tool's tail (`.crdownload`, `.part`, `.aria2`, and so on, the same list as `remove-broken`), a file with its marker file beside it (`x.mp4.aria2` beside `x.mp4`), and `x.mp4` inside a Safari marker folder (`x.mp4.download`). If the name changes, the download tool cannot find the file.
- **It does not change the inside of folders that programs look up by name.** Like `flatten`, these are program folders (`node_modules`, `__pycache__`, and so on), folders that hold a project marker file (`package.json` and so on), folders that hold an executable and a DLL together, and folders with the hidden attribute. It also does not change a saved web page (`page.html`) and its `page_files` folder. It reports once per folder, only when there is a file that would change. If the target is inside a program folder, or directly inside the target there is a project marker file or an executable and a DLL together, it refuses.
- **It also refuses when a folder above the target is a project or program folder** (#167). The criterion is the same as the check of the folder above in `flatten` (#148). If `myproj/package.json` exists, it does not handle `myproj/src` and `myproj/src/a`, and if `App/a.exe` and `App/b.dll` exist, it does not handle `App/sub`. It does not look at marker files directly inside a drive root, the user folder and above, or a default folder such as `Downloads` and `OneDrive\Desktop`.
- **Check with the preview first.** It cannot recognize program files not listed above or files linked by name.
- **There is no undo.**

## Collapse consecutive folders

`fctl collapse <target>` collapses a stretch where each folder holds only one folder. `a/b/c/file` becomes `a/file`. You can check first with `--dry-run`.

- **It keeps the top folder name.** The names of the middle folders disappear.
- **If a level has several items, it keeps the structure.** Hidden files also count as items. A stretch that continues below it is collapsed separately. It does not collapse the target itself. It does not touch a stretch that ends in an empty folder.
- **Names do not collide.** It moves the bottom folder as a whole, so it does not move files one by one.
- **If a product number would disappear, it does not collapse.** If the product number in a middle folder name is not in the top folder name and is not in the name of any video inside (or of any file, if there is no video), it skips and reports. For a folder with videos, you can collapse it by running `product-number` first. It protects only the formats that `src/product.js` recognizes.
- **The empty folders it clears are sent to the Recycle Bin.** If it cannot send them, it keeps the collapsed result and reports that a `.fctl-old-*` folder remained. On a volume that is not a fixed disk or whose Recycle Bin setting is "remove immediately", it does not send, so that nothing is deleted permanently (#81), and this folder remains.
- **What it skips**: leftovers, system folders, a stretch that holds a link, and a stretch that contains such an item. If a repository is inside, it refuses everything, the same as `flatten`.
- **If an inner stretch fails, the stretch above that contains it is not collapsed either.**
- **It does not collapse a stretch that holds a hidden folder** (#85). When it collapses, the bottom folder is moved to the top name, so the folder attributes and ACL (permissions) become those of the bottom folder. If the top is hidden the hiding is lifted, if the bottom is hidden the top name becomes hidden and looks gone, and if a middle one is hidden the inside is exposed, so if any folder of the stretch is hidden it skips with a reason. It reads the attributes with PowerShell in one go (only when there is a stretch to collapse, enumerating only the parents of the stretch folders, about 0.5 second), and if it cannot read them it collapses nothing and reports an error. The system attribute follows the bottom folder along with the folder icon (`desktop.ini`), so it is not blocked. In this case, if `desktop.ini` has a display name (`LocalizedResourceName`), Explorer shows that display name instead of the top name. It does not recognize folders with a different ACL, and the bottom folder's ACL remains (not tested). On other operating systems it does not look at attributes.
- **There is no undo.**

## Find broken files

`fctl find-broken <target>` only looks at the files under the target. It does not touch files.

- **Broken**: a video, image, document, or archive file of size 0, a file whose beginning is all zeros or whose content is a web page, and a truncated or structurally damaged video or archive. For the `.tar` family, it is the case where `tar.exe` reported it as truncated or damaged.
- **Suspicious**: a file that may be fine. A file whose first bytes do not match the extension (only the name changed, or a different packaging such as a password-protected Office document), a file whose structure is intact but has other data attached after it, and an empty file of an unknown format (`__init__.py`, `.gitkeep`, and so on).
- **Could not judge**: a locked or unreadable file, a file where `tar.exe` failed for a reason other than damage (a name not in the code page and so on), an archive with too many entries or that takes more than 10 minutes to read, and a fragmented MP4 with a very large number of boxes. They are not seen as broken files. For a compression that `tar.exe` extracts with an external program, such as lz4 and lzop, if that program is missing it reports "could not judge" naming the program, and if the program exists but fails, it cannot tell file damage from a program problem, so it also leaves it as "could not judge" (#245).
- **Formats it examines**: `.mp4`, `.m4v`, `.m4a`, `.mov`, `.3gp`, `.3g2`, `.mkv`, `.mka`, `.webm`, `.avi`, `.wav`, `.webp`, `.wmv`, `.wma`, `.asf`, `.flv`, `.flac`, `.ogg`, `.oga`, `.ogv`, `.opus`, `.jpg`, `.jpeg`, `.jfif`, `.png`, `.gif`, `.bmp`, `.tif`, `.tiff`, `.pdf`, `.zip` and Office documents (`.docx`, `.xlsx`, `.pptx`, `.odt`, `.ods`, `.odp`), `.epub`, `.jar`, `.apk`, `.7z`, `.rar`, `.gz`, `.bz2`, `.xz`, `.tar` and its compressed forms. For other files, it only checks whether the size is 0.
- **What it leaves out**: removal records (`fctl-removed-*.json`) and the inside of repository folders (`.git` and so on) are left out silently. Links, leftovers, and files inside system folders are reported as skipped.
- **Damage it cannot catch**: it looks only at the front structure. It does not check damage inside the video data, the body of images and PDFs, the content of `.zip` and `.7z` entries (CRC), or the content of stand-alone `.rar`, `.gz`, `.bz2`, and `.xz` files. Even for a compressed tar, it can miss a changed body. No "broken" result does not mean the file is intact.
- **Files being downloaded**: a video that was not downloaded to the end usually shows up as broken. Check that it is not being downloaded. However, the files of tools that reserve the size in advance (the front is normal, the back is 0) can show up as normal for an MP4 with `moov` at the front, an MKV with a fixed size, `.7z`, and `.tar`.
- **Normal files that show up as broken**: a piece of a GNU multi-volume `.tar` and a `.zip` with more than 70KB appended after the file cannot be told apart from truncated files. An `.xlsx` that starts with `<html` (a file that exported an HTML table under an Excel name) also shows up as broken.
- **Reading cost**: `.tar` and its compressed forms are read to the end, so a large one takes long. Reading an OneDrive online-only file can trigger a download.

## Remove broken files

`fctl remove-broken <target>` sends the files that `find-broken` reported as broken to the Recycle Bin.

- **It does not delete without a confirmation value.** It first shows the list and a confirmation value. After checking whether any of the "normal files that show up as broken" above are in it, run again with `--yes=<confirmation value>`. If you also pass `--dry-run`, it does not delete.
- **It deletes only if the list it saw is unchanged.** It judges again, and if even one of the path, reason, size, time, and file ID of a file to delete changes, or the files to delete increase or decrease, the confirmation value changes. Then it deletes nothing, shows the new list and the new confirmation value, and ends with exit code 1. Windows writes the modification time in clock ticks. The tick varies from about 0.5ms to 16ms depending on the running program. So a file rewritten with the same size within the same tick as the judgment, with the modification time set back, cannot be told apart by these values (#116). However, such a file has a modification time of just now, so it remains under the 5-minute protection below (except on exFAT; see "Files it keeps" below).
- **It writes the record first.** It writes `fctl-removed-<date>-<time>.json` (path, size, reason) in the target and then moves. If it cannot write the record, it deletes nothing. The record lists what is to be removed and does not write the result, so check the command output for files that could not be moved.
- **It does not delete suspicious files or files that could not be judged.**
- **It does not handle repositories.** If the target is a repository folder or contains a repository, it refuses. It does not block an ordinary subfolder of a repository.
- **Files it keeps**: a file whose latest of the modification, creation, and change times is within 5 minutes (it may be downloading or just copied), a file whose time is in the future, a file that changed after the judgment, a file with a name that cannot be deleted, and a file that has a download tool's marker file beside it.
- **It does not delete on a volume without a change time** (#184). On exFAT the change time is always the same value, and the creation time does not change by rewriting (#120). So a file rewritten in place with the same size and with the modification time set back evades both the 5-minute protection above and the confirmation-value comparison. So even if the target's drive is a fixed disk, if the file system is FAT, FAT32, or exFAT, or the file system cannot be determined, it reports every file to delete as "Kept" and does not delete. Move it from another PC or copy it to an NTFS volume, then delete. The file system is judged from the volume of the drive letter. Under a volume mount folder, the value of the drive where that folder lives comes out, so it cannot block. `remove-duplicates`, `remove-low-quality`, and `extract-all --remove-archives` are the same.
- **Progress display** (#99): on a real delete, for each file it reports on standard error how far along it is and the result, like `3/120 Move to the Recycle Bin: a.mp4`. It sends 100 at a time with one PowerShell run (#194), so a progress line appears each time a batch ends. On build 26200 it took 1.0 second for 20, 1.6 seconds for 50, and 5.5 seconds for 200 (when PowerShell was started for each file, 12 seconds for 20 and 27 seconds for 50).
- **Even when sent in a batch, it checks again right before deleting** (#194). Node checks each file right before sending the batch, and PowerShell also checks, for each file right before deleting, the real path (that a folder above was not replaced by a junction), that it is still a file, and that its size, change time, and file ID are the same as at the judgment. If even one differs, it does not delete that file and reports a failure. Interrupting a Recycle Bin move midway can lose files, so there is no time limit. For a file whose result PowerShell could not report because it ended midway, it reports "PowerShell did not report a result". Links are refused only if they are symbolic links or junctions, like Node, so files in the OneDrive folder (which carry a reparse attribute) are also deleted. A file with a modification time before 1970 is read differently by Node (v24), so it always remains with "Kept because the file changed after it was judged". `remove-duplicates` and `remove-low-quality` also send in batches the same way (#216).
- **Right before deleting, it also checks the volume's Recycle Bin setting again** (#236). After the plan-stage judgment (#100), the user may have set the volume's Recycle Bin to "remove immediately" or reduced its maximum size. PowerShell reads the setting once, the first time it meets each volume in a batch, and for each file right before deleting it makes the same judgment as `rm` (whether it is a fixed disk, whether it is remove-immediately, whether the size exceeds the maximum size, and, if the maximum size is unknown, whether it is 1GB or more). If it would be deleted permanently, it does not delete and reports "Not sent to the Recycle Bin" with the reason as a failure.
- **Files it keeps because they cannot be sent to the Recycle Bin** (#101): a file that is certain to fail on sending is moved to "kept" in the list in advance.
  - A file whose full path is 260 characters or more. A Windows Recycle Bin move accepts only up to 259 characters (a Korean name counts the same by character count). Shorten the name or move it to a folder above, then run again. `rm` also refuses such a path with the reason stated.
  - If two or more hard-link names of the same file are in the list, it deletes only one. Sending one name to the Recycle Bin changes the file's change time, so the other names look different from the judged file. The remaining names are deleted one at a time each time you run again after 5 minutes. When nothing is deleted because of the volume, it keeps them with the volume reason. If the other name is only outside the target, it deletes as is.
- **A download tool's marker files**: if a file or folder with a marker after the file name (`x.mp4.part` for `x.mp4`) exists in the same folder, the file may be downloading even when old, so it keeps it and writes the marker file name in the reason. The markers are `.part`, `.part-Frag<number>`, `.crdownload`, `.partial`, `.download`, `.opdownload`, `.fdmdownload`, `.aria2`, `.ytdl`, `.td`, `.td.cfg`, `.xltd`, `.!qB`, `.!ut`, and `.bc!`, and case does not matter. It also keeps the case where, like Safari, a file being downloaded sits as `x.mp4` inside an `x.mp4.download` folder. If it cannot read the folder to check for marker files, it keeps the files of that folder. For a file whose download was abandoned, delete the marker file and run again. It cannot recognize tools that put a file being downloaded in a separate temporary folder or download without markers (IDM, a torrent program with markers turned off, and so on).
- **Files it keeps to avoid permanent deletion** (#100): it reads that volume's Recycle Bin setting (per user, `BitBucket\Volume\{GUID}`), and keeps, without deleting, a file when "Don't move files to the Recycle Bin. Remove files immediately when deleted" is on or when the file is larger than the Recycle Bin maximum size. When tested on build 26200, in both cases Windows deleted permanently without asking and finished as a success (with a D: maximum size of 7164MB, a 7100MB file went to the Recycle Bin and a 7200MB file was deleted permanently). The amount already in the Recycle Bin did not matter (even when the total exceeded the maximum size, it neither emptied existing items nor deleted the new file permanently). If it cannot read the setting, it keeps files of 1GB or more as before. If the Recycle Bin was turned off by policy (`NoRecycleFiles`), it is treated as remove-immediately, and if the size was set by policy (`RecycleBinSize`), the size is treated as unknown. The volume is found with `GetVolumePathName`, so under a volume mount folder it looks at that volume's setting (not tested with a mount folder). It also keeps files on a volume that is not a fixed disk or whose type could not be determined. A USB external exFAT disk (E: on this PC) looks like a fixed disk and its Recycle Bin also worked, but because it is exFAT, it is kept by the change-time check below.
- **It deletes only in an interactive session.** In a non-interactive run, it stops before writing the record.
- **OneDrive folder**: the sync changes a file's change time. So during a sync the 5-minute protection can extend or the confirmation value can mismatch. It acts in the direction of not deleting, so run again a moment later.
- **Exit code**: it is 1 if there is a file that could not be sent to the Recycle Bin, if the confirmation value does not match, or if there are files to delete but `--yes` was given no value. Showing the list without `--yes`, and the case with only kept files, are 0.

## Find duplicate videos

`fctl find-duplicates <target>` groups the video files under the target by name and by length and shows duplicate candidates. It does not touch files. For each file it shows the size, resolution, and length together, and attaches `[kept: <reason it was chosen>]` to the one file to keep in each group. Removal is done with `remove-duplicates` (below).

- **Grouping by product number**: if the name has exactly one upper-case product number (`ABC-123`), it groups by the number. It is the same group even if the extension, folder, quality mark, title, or `(1)` tail differs. `ABC-123.mp4` and `sub/[FHD] ABC-123 Title 1080p.mkv` are such a case.
- **Pieces are grouped separately**: it reads piece marks broadly so that different videos are not put in one group. It splits what remains after removing the number into words, and treats as pieces a digit inside a word (`CD2`, `part 1`, `-1`, `[2]`, `Title 3`, `Episode 01`, `1.5`), a circled digit (`①`), a one-letter English word (`ABC-123 B`, `(A)`, `[A]`, `Title A`, `Part I`), a Roman numeral of two or more letters (`II`, `xiv`) and a Roman numeral character (`Ⅲ`), and `前編`, `後編`, `上巻`, `下巻`, `상`, `하편`, `전편`, and `第一話` (Japanese and Korean words for "first half", "second half", "volume 1", "volume 2", "upper", "second part", "first part", and "episode 1"). It leaves out quality and codec marks (`1080p`, `60fps`, `10bit`, `4K`, `x264`, `HEVC`, `AAC2`, and so on), a trailing `(1)`, and copy tails. `part 01`, `-1`, and `①` are the same piece 1, and `III`, `Ⅲ`, and `③` are the same piece 3. So `ABC-123 CD1`, `ABC-123 CD2`, and `ABC-123` are different groups. In exchange, the same video with a digit or a one-letter word in the title (`ABC-123 2023`, `ABC-123 A Day`), or the same video with an audio mark that contains a dot such as `5.1ch` and `AAC2.0`, is grouped separately and a duplicate can be missed.
- **Grouping by name when there is no number**: from the name without the extension, it ignores differences of case, full-width characters, composed Hangul, spaces, dots, underscores, and hyphens, and Explorer's copy tails (` - 복사본`, ` - Copy (2)`; `복사본` is Korean for "copy"). `My Movie.mp4`, `my_movie.MKV`, and `My Movie - 복사본.avi` are the same group. `My Movie (1).mp4` may be a different video, so it is not grouped.
- **What it does not group**: a name that holds several different numbers is reported as "Several numbers". A lowercase number (`abc-123`) is not seen as a number and is grouped by name. If you first change it with `normalize --include-lowercase`, it is grouped by number.
- **Files it looks at**: the same video extensions as `product-number`. `.ts` and `.mts` are looked at only when the content is MPEG-TS. Links, leftovers, and files inside system folders are reported as skipped, and the inside of repository folders (`.git` and so on) is left out silently. Removal records (`fctl-removed-*.json`) are not videos, so it does not look at them.
- **A name does not look at content**: a name group does not check whether the content is the same. So different videos can be in one group. It compares the length and resolution within the same group. For the groups below, it adds a `Caution:` line after the file lines, and counts them as "need checking" groups on the last line (#103).
  - **Common names such as camera and sequence names**: groups whose names become the same even for different videos in different folders, such as `IMG_0001.MOV`, `GH010001.MP4`, `DJI_0001.MP4`, `1.mp4`, and `REC-0001.mp4`. The criterion is the same as in `remove-duplicates` below. "Caution: This is a common name such as a camera or sequence name, so videos with the same name may be different videos. remove-duplicates does not delete this group."
  - **Groups with the same number but different titles**: words that look like a product number (`WWE-2023 Raw` and `WWE-2023 SmackDown`, `IPHONE-15 review` and `IPHONE-15 unboxing`) are grouped under the same number. From what remains after removing the number, the words left after dropping digits, piece marks, quality, codec, and release marks (`1080p`, `FHD`, `HEVC`, `자막` (subtitles), and so on), and copy tails are seen as the title. For two files that have titles, if neither one's words are all contained in the other's, it adds "Caution: The number is the same but the titles differ, so they may be different videos. remove-duplicates deletes only files whose title words are identical to the file to keep in this group." `Good Movie` and `Good Movie Director's Cut` are the same title, and a partial overlap such as `WWE Raw` and `WWE SmackDown` is a different title. If only one side has a title (`ABC-123.mp4` and `ABC-123 Title.mkv`), it is not seen as different. A file of the same video that was given a title in other words (another language, a title with words added or removed, and so on) can also be seen as different.
  - **Groups with different lengths**: see "Name groups with different lengths get a caution" below.
- **Grouping by length**: even if the names differ, videos whose length differs by 1 second or less and whose aspect ratio (visible width / height) is within 3% are grouped as "videos of the same length". The aspect ratio in the report is written to one decimal place. The resolution and size may differ, because re-encoding the same video changes both. If the size is also the same, it adds ", same size too".
- **What it does not group by length**: a video shorter than 60 seconds (the length of short clips is often the same by chance), and a video whose length or resolution could not be read. The length is read only for `.mp4`, `.m4v`, `.mov`, `.3gp`, `.mkv`, and `.webm`. `.avi`, `.wmv`, `.flv`, `.ts`, and so on count as "unknown duration". So that no two files in a group differ by more than 1 second, it adds files only up to 1 second from the shortest file. A file in a format whose length can be read, such as `.mp4` and `.mkv`, but whose length or resolution could not be read (a structurally broken file, a fragmented MP4 that does not record the length or an MKV/WebM whose recording was interrupted, a file with no video track) is shown as "Could not read duration/resolution" with the reason.
- **The aspect ratio is computed from the visible size** (#106): the resolution is shown by the stored value, and if the visible size differs because of rotation or pixel aspect ratio, it writes both, like `1920x1080 (displayed size 1080x1920)`.
  - **Rotation**: for 90 or 270 degrees, it swaps the width and height. So a video that a phone stores as landscape and shows as portrait (1920x1080 + 90 degrees) is grouped with a copy saved again as portrait (1080x1920) and is not grouped with a landscape video of a similar length.
    - MP4/MOV: it looks at the track matrix (tkhd) and the whole-movie matrix (mvhd) together. If both are 90 degrees, they add up to 180 degrees, so it does not swap (#113).
    - MKV/WebM: it looks at `ProjectionPoseRoll` of a flat projection (`ProjectionType` 0). FFmpeg writes rotation this way (#113). It uses it only when it is within 1 degree of a multiple of 90. A projection of 360-degree video, a projection tilted up and down (`Pitch`), and a projection turned left and right by an angle other than 180 degrees (`Yaw`) are not screen rotation, so it does not look at them.
  - **Pixel aspect ratio**: DVD 16:9 (720x480, visible size 853x480) is grouped with 16:9 video.
    - For MP4/MOV, it uses the first value found in the order below (#113). It uses the container's value before the value in the video data. For 1 and 3, it multiplies the width by the pixel aspect ratio, and for 2, it uses that size as it is.
      1. `pasp`. If it is 1:1, it is seen as square pixels.
      2. If the track display size (tkhd) differs from the encoded resolution, that size. There are files that reflect the pixel aspect ratio only in this size, without `pasp`. A file that writes the coded size (1920x1088) and writes 1920x1080 in tkhd is also seen as 1920x1080. A size that changed the width and height by the same factor is seen as pixel aspect ratio 1 and the encoded resolution is used. A file of a rotated video that wrote the size after rotation in tkhd (the ratio with width and height swapped) is not seen as a pixel aspect ratio and moves on to 3. It also does not use a tkhd size whose integer part is 0.
      3. The pixel aspect ratio (VUI) in the SPS inside `avcC` (H.264) or `hvcC` (HEVC) of the sample entry. In some files made with ffmpeg, the pixel aspect ratio is only here, without `pasp`. It does not read the video data (`mdat`), and it reads the SPS only up to the pixel aspect ratio. An unreadable SPS is seen as square pixels. It was confirmed to read the same values as ffprobe on 19 kinds of SPS made with x264, x265, and Intel QSV (#123). Apple VideoToolbox output has not been confirmed yet (#126).
    - MKV/WebM: it first subtracts the pixels to crop (`PixelCrop*`). Then, if `DisplayWidth`/`DisplayHeight` exist, it uses that ratio (when the unit is pixels, cm, inches, or an aspect ratio). By the specification this value is the size after cropping, and if it is absent, the cropped size is the visible size. A video cropped by 8 lines below from 1920x1088 is seen as 1920x1080.
  - **Within 3% counts as the same**: comparing by rounded cells would split the same video that sits on a boundary, such as 1920x816 and 1920x818, so if the wider side is within 3% wider than the narrower side, it counts as the same. 16:9 (1.78) and 1.85:1 differ by nearly 4%, so they are not grouped. So that no two files in a group differ by more than 3%, it adds only files within 3% of every file in the group. A file goes into only one group, so if another video whose length and ratio are both close makes a group first, a pair of the same video can be split and drop out of the report.
  - **What it does not look at**:
    - The pixel aspect ratio inside the video data of MKV/WebM (the SPS in `CodecPrivate`). By the specification, if `DisplayWidth`/`DisplayHeight` are absent, the cropped pixel size is the visible size. FFmpeg 9.0 also sees an MKV that has 32:27 in the SPS and no `DisplayWidth` as 1:1 (confirmed in #123).
    - Stretching in an MP4/MOV matrix (a matrix whose horizontal and vertical scales differ) and rotation that is not a multiple of 90.
    - The crop information of MP4/MOV (`clap`).
    - The pixel aspect ratio inside the video data of codecs other than H.264 and HEVC (MPEG-4 Part 2, AV1, VP9, and so on).
- **It does not repeat**: if every file of a length group is already in one name group, it does not show it again as a length group.
- **Videos of the same length can be different videos**: a broadcast recording with a fixed length, or videos cut to the same length, are grouped even when the content differs. It does not compare the content (the video data).
- **Choosing the file to keep**: it looks at the criteria below in order, and for each criterion only the best files pass to the next criterion.
  1. A file in a format whose length can be read, such as `.mp4` and `.mkv`, but whose length or resolution could not be read may be broken, so it is moved to the back. A format that is not read, such as `.avi`, is not moved back.
  2. Among the files left from 1, a file more than 1 second shorter than the longest file whose length is known may be a copy that was not fully downloaded or was truncated, so it is moved to the back.
  3. The file with the highest resolution (width x height in pixels). A file whose resolution is unknown comes after one whose resolution is known.
  4. The file with the largest size.
  5. The file with the shortest name. It is likely to be the original file with no copy tail (` - 복사본` ("copy"), ` (1)`, ` copy`) attached.
  6. The first file in path order (the same as the report order of the name groups. Length groups are shown in length order, so it can differ).
- **Name groups with different lengths get a caution**: if files in a name group whose lengths are known differ by more than 1 second, it shows "Caution: The durations differ, so they may not be the same video." It still chooses the file to keep, but you must check that the rest are really copies (#103).
- **It chooses separately for each group**: if one file is in both a name group and a length group, it can be kept in one and not kept in the other. Quality is judged only by resolution and size. It does not look at the codec (H.264, HEVC, and so on) or the bitrate.
- **Reading cost**: it reads only the head structure of the video, but reading an OneDrive online-only file can trigger a download.

## Remove duplicate videos

`fctl remove-duplicates <target>` leaves one file to keep for each name group of `find-duplicates` and sends the copies of that file to the Recycle Bin.

- **It does not delete without a confirmation value.** It first shows, for each group, the file to keep, the files to delete, the files it keeps, and a confirmation value. After checking the list, run again with `--yes=<confirmation value>`. If you also pass `--dry-run`, it does not delete.
- **It deletes only copies that match in both name and length.** Among the files of a name group, it deletes only those whose length differs from the file to keep by 1 second or less and whose aspect ratio is the same (within 3% in the visible size, by the same criterion as `find-duplicates`). A different video with only the same name (a trailer with the same number, `WWE-2023 Raw` and `WWE-2023 SmackDown` that look like a product number) is kept if the length or ratio differs. A file whose length or resolution is unknown (`.avi` and so on) and a file shorter than 60 seconds are also kept, because it cannot be checked that they are the same video. If the length of the file to keep is unknown, it deletes nothing from that group. If a group has files of different lengths, it also shows a `Caution:` line.
- **It does not delete files that have the same number but a different title.** In a number group, a file whose title differs from the file to keep (by the same criterion as `find-duplicates`) is kept even if the length and the aspect ratio are the same. This is the case with broadcast recordings of a fixed length (`WWE-2023 Raw` and `WWE-2023 SmackDown` are both 3 hours) (#103). In a group where files with a different title are mixed, it deletes only when both the file to keep and the file to delete have a title and the title words are exactly the same (`XYZ-999 Good Movie.mp4` and `XYZ-999 Good Movie 1080p.mp4`). If the file to keep has no title, such as `WWE-2023.mp4`, or the title is contained in both titles, such as `WWE-2023 WWE.mp4`, it does not know which of Raw and SmackDown it is a copy of, so it keeps both. In a group with no files of a different title, it deletes even when one side has no title (`QRS-100 Title.mp4` and `QRS-100.mp4`) or a title with words added (`Good Movie` and `Good Movie Director's Cut`).
- **It does not delete common names such as camera and sequence names.** A group whose key value, after removing one leading English word (up to 10 characters), has only mostly numeric words (like `e0001` and `000001f`, with up to 4 English letters in front and up to 2 behind) and English words of 1 to 2 letters (`IMG_0001.MOV`, `IMG_E0001.MOV`, `GH010001.MP4`, `DJI_20230101123456_0001_D.MP4`, `FILE0001.MOV`, `VID_20230101_123456.mp4`, `20230101_123456_F.mp4`, `1.mp4`) is kept even when the length and aspect ratio are the same. Dashcam pieces and recordings split by time have a fixed length, so different videos on different SD cards can have the same name and the same length (#103). Names that a person gave, made of one word and a number such as `Video 1.mp4`, `Joker 2019.mp4`, and `EP01.mp4`, also fall here and are kept. Recorder counters made of upper case letters and hyphens are grouped as product numbers, so if the prefix is in a fixed list (`REC`, `CAM`, `MOVI`, `FRONT`, `REAR`, `EVT`, `PARK`, `NORMAL`, and so on), that number group is also kept (`REC-0001.mp4`, #110). A counter with a prefix not in the list is treated like a product number and can be deleted.
- **It deletes only when the file to keep looks intact.** The file to keep is chosen by resolution and size, so a partly downloaded file with a high resolution can become the file to keep. So it runs the same judgment as `find-broken` on the file to keep, and if broken or suspicious comes out (a truncated file, a file with no position table, and so on), it does not delete that group. For a file of 1MB or more, it reads 4KB at each of 16 places, and if there is a stretch filled only with zeros, it may be a download that stopped with only the size reserved, so it does not delete (#109). It does not read all the data, so it cannot catch a file that is only partly damaged. Check the file to keep in the list, then run.
- **It does not delete files that may be downloading.** It looks at the same download tool marker files as `remove-broken` (`x.mp4.part`, `x.mp4.aria2`, and so on) and Safari's `x.mp4.download` folder (#115). For a file whose download was abandoned, delete the marker file and run again.
  - If a marker is beside the file to keep, it deletes nothing from that group. A file that reserves the size in advance, like aria2, already has the head structure downloaded, and if the zero-stretch samples happen to land only on the downloaded places, it looks intact. Below 1MB it does not take samples either.
  - If a marker is beside a copy to delete, it keeps only that copy.
  - If it cannot read the folder to check for markers, it keeps them too. If it is the folder of the file to keep, it keeps that group, and if it is the folder of a copy, it keeps that copy.
  - If a marker file appears after the confirmation value was made, it deletes nothing.
- **It does not delete groups that match only by length.** If the names differ, videos can be different even with the same length. It only reports the count and has you look with `find-duplicates`. So files do not overlap between name groups, and a file kept in one group is never deleted in another.
- **It deletes while protecting the file to keep.** If the file to keep changed within 5 minutes or its time is in the future, it does not delete that group. The confirmation value also includes the time of the file to keep, so if the file to keep changes after the confirmation value was made, it deletes nothing. Even while deleting, for each copy it checks again that the file to keep is still there, and if it is gone or changed, it does not delete that copy and reports a failure.
- **It writes the record first.** It writes `fctl-removed-<date>-<time>.json` in the target and then moves. For each item it writes the path, size, and reason, and in `details` the file to keep (`keep`) and the group name (`group`).
- **The other safety measures are the same as `remove-broken`.** Copies that are certain to fail when sent to the Recycle Bin, or that are useless to delete, are kept in the plan (#127).
  - A path that cannot be sent to the Recycle Bin: a copy whose full path is longer than 259 characters or that holds a name ending in a dot or a space. It is the same check as `rm`.
  - A copy that is another name of the same file (a hard link) as the file to keep: deleting it does not reduce space, and deleting it changes the change time of the file to keep, so the next copy of the same group fails with "the file to keep changed". It reports it as "another name of the same file" and does not delete it.
  - A copy that is the same file as another copy to be deleted this time: it deletes only one at a time (the same as `remove-broken`). The remaining names are deleted when you run again after 5 minutes.
  - Besides that: it does not handle repositories. It keeps a copy that changed within 5 minutes, a copy that would be deleted permanently by the Recycle Bin setting (remove immediately, over the Recycle Bin maximum size, 1GB or more if the setting cannot be read), and a copy on a volume that is not a fixed disk (#81, #100). It deletes only in an interactive session. The exit code is also the same. It does not delete on a volume whose file system is FAT, FAT32, or exFAT or could not be determined (#120, #184).

## Find low-quality videos

`fctl find-low-quality <target>` finds the videos under the target whose resolution or bitrate is below the standard (#30). It does not touch files.

- **The standards are set with options.** `--min-height=<pixels>` (default 360) is the standard for the shorter side of the screen, and `--min-bitrate=<kbps>` (default: not checked) is the standard for the bitrate. If it is below either one, it is low quality. Write the value as an integer of 1 or more (`--min-height=480`, `--min-bitrate=500`). They cannot be used with other commands.
- **The resolution is judged by the shorter side of the visible size.** It uses the visible size that reflects rotation and pixel aspect ratio (the same as `find-duplicates`). So a phone portrait video (1080x1920) is seen as 1080, the same as a landscape video 1920x1080.
- **The bitrate is the file size divided by the length.** It includes audio and the head structure. The bitrate of the same quality varies a lot depending on the codec and the content, so by default it is not checked.
- **The formats it reads are MP4/MOV and MKV/WebM.** Other videos such as `.avi` and `.wmv` are reported as "Undetermined". It does not look at images yet.
- **A broken value is not seen as low quality.** A resolution whose shorter side is under 16 pixels or whose longer side is over 65535 pixels, a length over 7 days, a bitrate under 1kbps, and a visible size that differs from the encoded resolution by more than 2 times (when a broken tkhd makes 1920x1080 look like 1920x100) are seen as broken values and reported as "could not judge". If the length is under 1 second, it does not trust the bitrate. If the resolution is already below the standard, it is low quality even if the bitrate is unknown.
- **If the length and the data do not match, it does not trust the bitrate** (#179). In the cases below, it leaves the bitrate as "could not judge" and reports the reason.
  - MP4: a file whose written length (mvhd) is longer than 2 times the longest of the sums of the track sample tables (stts) plus 60 seconds. A 60-second video written as 60000 seconds is such a case. The empty stretches of an edit list or the length differences between tracks are smaller than this. A partly downloaded file whose data position table (stco, co64) points past the end of the file is the same.
  - MKV: a file whose written length is longer than 2 times the last time of the seek table (Cues) plus 60 seconds. A partly downloaded file whose Segment size or the position that SeekHead or the seek table points to goes past the end of the file is the same.
  - Cases it cannot cross-check: a fragmented MP4 (the sample table of moov is empty), an MP4 with no sample table, an MKV whose seek table is missing, has only one entry, or has a last time of 0 (a screen recording that put keyframes only at the start, a music file with a single still picture, and so on; the time of the last Cluster is not looked at because it would require scanning the video data), and a partly downloaded MP4 whose moov is at the end of the file (here moov is missing, so it is already "could not judge"). A written length shorter than the real one gives a high bitrate and is not wrongly caught as low quality, so it is not looked at.
  - Normal files that become "could not judge": a MOV whose playback speed was stretched slower than 0.5 times with an edit list (the written length exceeds 2 times the sample table plus 60 seconds), and an MKV with a very long keyframe interval. They are not wrongly caught as low quality.
  - This check is made only in the low-quality judgment (`find-low-quality`, `remove-low-quality`) (#207). `find-duplicates` and the product-number search, which do not use the bitrate, do not read the sample table and data position table of MP4 or the seek table of MKV.
- **What it skips**: links, leftovers, files inside system folders, and files inside repository folders (`.git` and so on). The same as `find-duplicates`.

## Remove low-quality videos

`fctl remove-low-quality <target>` sends the low-quality videos found by the same standards as `find-low-quality` (`--min-height`, `--min-bitrate`) to the Recycle Bin (#31).

- **It does not delete without a confirmation value.** It first shows the files to delete (resolution, length, bitrate, and the standard that applied), the files it keeps, the files it could not judge, and a confirmation value. After checking the list, run again with **the same standards** and `--yes=<confirmation value>`. The confirmation value also includes the standards, so if you change or omit the standards, it deletes nothing. If you also pass `--dry-run`, it does not delete.
- **It deletes only files caught by the resolution standard.** A file that is low quality only by bitrate is shown in the list as "Kept" and is not deleted. The bitrate is the file size divided by the length, so if the length is read inflated or the file was partly downloaded, even a normal video comes out low. It will be decided again when the check that cross-checks the length (#179) exists.
- **It does not delete files it could not judge.** These are broken metadata values and formats it cannot read (`.avi` and so on).
- **It writes the record first.** It writes `fctl-removed-<date>-<time>.json` in the target and then moves. For each item it writes the path, size, and reason, and in `details` the resolution (`width`, `height`), the visible size (`displayWidth`, `displayHeight`), the length (`duration`, in seconds), the bitrate (`bitrate`, bits per second), and the standards used (`criteria`).
- **The other safety measures are the same as `remove-broken`.** It keeps a file that changed within 5 minutes, a file with a download tool's marker file beside it, a file that would be deleted permanently by the Recycle Bin setting (remove immediately, over the Recycle Bin maximum size, 1GB or more if the setting cannot be read, #219) and its hard-link names, a file over the Recycle Bin path limit, a file whose other name (a hard link) of the same file is already in the list to delete first, and a file on a volume that is not a fixed disk. It does not handle repositories. It deletes only in an interactive session. Even if one file fails, it continues with the rest, and if there is a failure it ends with exit code 1. It does not delete on a volume whose file system is FAT, FAT32, or exFAT or could not be determined (#120, #184).

## Extract all archives

`fctl extract-all <target>` extracts each archive under the target (`.zip`, `.tar`, `.tar.gz`, `.tgz`, `.tar.bz2`, `.tbz2`, `.tar.xz`, `.txz`, `.7z`, `.rar`) into a new folder beside it. `a.zip` becomes `a/`. You can check first with `--dry-run`.

- **It keeps the archives by default.** It also does not extract again an archive that came out of an extraction.
- **`--remove-archives`**: it sends the `.zip`, `.7z`, `.tar.gz`, and `.tgz` that were extracted normally to the Recycle Bin. It does not delete archives that were skipped or failed. So if an extracted folder already exists, the original stays too.
  - `.tar.gz` and `.tgz` are extracted successfully by `tar.exe` even if the body changed, so a separate Node process reads the whole file again as a stream to check (#197). For gzip it looks at the CRC and length of each member, and if it is truncated or has data that is not gzip attached after it (including zero-filled data), it keeps it. For tar it looks at the header checksum, the data of the size of each entry, and the end marker (zero blocks), and if there is no end marker or there is nonzero data after it (including an appended tar.gz; `tar.exe` stops at the end marker and does not extract what comes after), it keeps it. It also checks that the number of entries matches the `tar.exe` list and that each entry was extracted with that name (including pax UTF-8 names and GNU long names) and size. It keeps it if a non-pax name has non-ASCII bytes, if there is an entry kind that cannot be checked from the extracted result such as a sparse file, if there is an empty pax name, or if there is a hard link with content. It does not look at the size of a hard link entry.
- **Cases it keeps even with this option**: in the cases below it only extracts and reports "Kept".
  - Other formats (`.tar`, `.tar.bz2`, `.tbz2`, `.tar.xz`, `.txz`, `.rar`). `tar.exe` does not catch damage, does not read some parts, or it could not be confirmed whether it catches them.
  - A file whose content differs from the extension, a `.zip` that is truncated or has other data attached before or after, a `.7z` that has other data attached after it, split archive pieces, a `.zip` with data between entries that is not in the central directory, and a `.zip` that has only a Zip64 marker and no Zip64 end record or one that does not match. A Zip64 `.zip` is checked the same way with the Zip64 end record and the extra field, and is deleted (#83).
  - A `.7z` that has an entry without a CRC (#198). `tar.exe` checks the content only of entries that have a CRC (it fails if the CRC is wrong), and if there is no CRC it extracts successfully even if the body changed. 7-Zip and `tar.exe` write a CRC for each entry. A 7z that has only a folder CRC and no entry CRC is also not checked by `tar.exe`, so it is seen as having no CRC and is kept. It also keeps it if the CRC of the 7z header is wrong, if the structure cannot be read, if there is data between bodies that is not in the list, or if there is an erase marker (anti) entry. For the header, it reads only LZMA, LZMA2 (what `tar.exe` made with `--options 7zip:compression=lzma2`, #222), and no compression, and it keeps a header compressed another way because it cannot read it.
  - A case where it could not confirm that it was extracted with its original name. Names that contain `:` or `?` fall here. For `.7z`, it checks the extracted result by the UTF-16 names and sizes in the header (extracting even a header compressed with LZMA or LZMA2), so it also deletes non-ASCII names (#198). For a `.zip` with a non-ASCII name that has no UTF-8 marker, it reads it in the OEM code page like `tar.exe` and checks that it was extracted with exactly that name (#83). So on Korean Windows (OEM 949), it also deletes a `.zip` with Hangul names made by Korean tools or `fctl zip`. In an environment where Node cannot read the OEM code page (437 on English Windows and so on), it keeps it. Node's CP949 interpretation misreads Hangul outside KS X 1001 (extended-area letters such as 똠 and 햏) as other characters, so a name that contains such letters is kept as an "item that was not extracted under the same name". The preview looks only at the name letters, so it can show such a zip as one it will delete.
- **It does not delete an archive that changed while extracting.** Before extracting, it writes down the file ID, size, modification time, and change time. If even one differs right before deleting, it reports a failure (the same identification values as `remove-broken`). Even if the file was rewritten in place with the same size and the modification time was set back, the change time changes and it notices (NTFS and ReFS. exFAT and so on are not deleted; see below).
  - The change time is written in clock ticks (about 0.5ms to 16ms) (#116). It cannot tell a rewrite within the same tick. However, the last change to the original is before extracting, and checking the content requires running `tar.exe` twice. A single list read alone took more than 17ms on this PC. So a swap after the check happens later than a clock tick.
  - Measurement (this PC, C: on NTFS and D: on ReFS): when an in-place rewrite that set back the modification time was done 20ms later, it was told apart in all 50 runs. At 0ms later, it could not be told apart in 14 of 50 runs on NTFS and in 38 on ReFS. Looking only at the file ID, size, and modification time as before, it missed all of them. The file ID on ReFS exceeds 2^53, so it is compared without losing precision.
  - **exFAT has no change time** (#120). On E: of this PC (an external exFAT attached as a fixed disk), the change time of every file came out as the same value (2009-04-22T19:24:48Z). So if a file is rewritten in place with the same size and the modification time is set back, the identification values stay the same and the swap cannot be told apart. The modification time was also written in seconds. This volume is detected as a fixed disk and passes the volume condition of the deleting commands. So `--remove-archives`, if the file system is FAT, FAT32, or exFAT or could not be determined, only extracts and reports every archive as "kept" (#184; see the `remove-broken` section). The preview is the same.
  - **FAT32 was not checked.** This PC has no FAT32 volume with a drive letter, and attaching a virtual disk for testing needs administrator rights. If FAT32 also does not record a change time, it is the same as exFAT. FAT and exFAT are usually USB sticks or SD cards, which have no Recycle Bin and can be deleted permanently (see "Recycle Bin caution" below, #81).
  - There is no 5-minute protection of `remove-broken`. An archive just downloaded is also deleted if it extracts normally. A partly downloaded `.zip` usually has no end marker, so it is kept or fails to extract. In the OneDrive folder, the sync changes the change time and it can be reported as a failure. Then the original stays, and an extracted folder exists, so it is skipped even if you run again.
- **If it extracted but could not send to the Recycle Bin**, it reports a failure and leaves the original and the extracted folder. The reason starts with "Extracted, but could not delete the original." followed by the reason the Recycle Bin move reported (in use by another program, a path longer than 259 characters, and so on) (#185). The preview starts with "Even if extracted", as in "Even if extracted, the original cannot be deleted.". If only the archive path is longer than 259 characters, it fails with this reason after extracting everything, but on Windows without long paths turned on, if the path of the temporary folder (`.fctl-new-*`) or of an extracted item exceeds 260 characters, `tar.exe` cannot extract, so it fails first at the extraction step.
- **Recycle Bin caution**: for an archive larger than the Recycle Bin maximum size, a volume whose Recycle Bin setting is "remove immediately", and a drive that is not a fixed disk, Windows deletes permanently without asking (#81; the first two were confirmed on build 26200). So it does not delete the original and reports a failure. The content is extracted in the new folder.
- **It does not merge.** If a folder or file of the same name exists, it skips and reports. So even if you run again, it does not extract again.
- **It exposes only what was fully extracted.** It extracts into a temporary folder (`.fctl-new-*`) and then renames. On failure, it deletes the temporary folder and reports a failure.
- **Cases it counts as failure**: a broken archive, a password-protected archive, a file with no entries, an entry that points outside the target with `..`, entries whose names overlap and lose some (including ones that differ only in case), names that Windows interprets differently such as `con.txt` or a trailing dot, and link and device entries.
- **Damage it cannot catch**: a `.tar.gz` can succeed even if part of the body changed (`--remove-archives` keeps it by the check above), and a `.tar` truncated at an entry boundary extracts only the remaining entries and succeeds. A `.zip` can also extract only part and succeed if the end is truncated or another file is appended. It reports the extraction as a success, but by the criteria above it does not delete the original.
- **The preview reads only the list.** Passwords, name overlaps, and unusable names can be known only by really extracting. However, to decide whether to delete, the `--remove-archives` preview also reads the structure of `.zip` and the whole of `.tar.gz` and `.tgz` (decompressing gzip to the end to check the tar structure). It does not compare against the extracted result.
- **Entry names**: `tar.exe` handles them. If there is a character not in the code page such as an emoji, or a tar made on Linux or macOS holds UTF-8 names as they are, it can fail (the preview can pass), and characters such as `:`, `?`, and `*` can be changed to `_` or the front part of the name can disappear.
- **There is no size limit.** It does not check the extracted size in advance, so the disk can fill up. Reading an OneDrive online-only archive can trigger a download.
